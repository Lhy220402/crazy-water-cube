## 4. 机制契约（改动前必读）

### 4.1 固定合成链与计分

| 材料 | 产物 | 基础分 |
| --- | --- | --- |
| 军 ×2 | 赢² | +4 |
| 赢² ×2 | 水³ | +8 |
| 水³ ×2 | Lec | +16 |
| Lec ×2 | OLD FIVE | +32（假通关） |
| OLD FIVE ×2 | 随机词条（图鉴 +1） | +64 |
| 任意词条 ×2 | 再随机一条词条 | +64 |
| 传奇 ×2（v3.0） | 再随机一条传奇（图鉴 +1） | +512 |

- 4×4；单步内每枚方块最多参与一次合成（不连锁）。
- 实际得分 = 基础分 × 当前增益倍率（四舍五入取整）。
- 词条之间**不看名字、不看稀有度**，同为词条级（rank=codexRank=5）即合。
- v3.0 的传奇是**更高一级**（rank=mythRank=6，`Tile` 带 `variant`），只能与传奇相合；
  传奇与 rank 5 词条 / 普通等级**不相合**（只滑动）。「任意两条词条都能合」仍只指 rank 5 那层。

### 4.2 特殊配方（相撞即合，无序匹配，优先于同级判定）

| 材料 | 产物 | 基础分 | 增益 |
| --- | --- | --- | --- |
| 隋 + 军 | 水军（v2.3 前叫「隋军」，id 仍 `sui-jun`） | +64 | ×2，持续 8 步 |
| 隋圆 + 军 | 隋军隋圆 | +128 | ×3，持续 12 步 |
| 隋 + 钢 | 水缸 | +128 | ×2，持续 8 步（与水军同一梯队） |
| Li + Na | 李娜 | +128 | ×2，持续 8 步（与水军同梯队） |
| 彪 + 水³ | 妙（v2.4） | +128 | ×2，持续 10 步；增益期间**每次有效移动**在妙所在格飘爱心粒子（跟随妙移动） |
| 记 + 赢² | 记赢赢 | +256 | **真通关** + 本局永久 ×2 |
| 记赢赢 + 会成 | 记会成（v2.5） | +256 | ×2，持续 10 步 |
| 记赢赢 + 记赢赢 | 随机传奇（v3.0，从 12 条传奇池抽） | +512 | 无增益；落成 rank 6 传奇方块 |

- 增益创建当步**不生效也不消耗**，从下一步开始倒数；多个增益乘算叠加。
- 显示名（v2.4）：隋圆（棋子写「隋」+ 圆环）、隋军隋圆（特殊产物）；内部 id 仍 `sui-ring` / `sui-jun-ring`，
  增益 label 同步成「隋军隋圆·洪峰」，旧档读档时按当前定义刷新 label。
- 特殊产物也是词条级方块：可与任意词条继续合成（被消耗时增益不撤销）。
- 特殊产物触发即收录图鉴；有解释文案的产物首次触发弹解释卡（隋 / 李娜没有文案，见 4.5）。
- 配方与产物定义集中在 recipes.ts；加配方只改那里 + lore.ts。
- v3.0 的传奇抽取走 `recipes.ts` 的 `MYTH_RECIPES`（`matchMythRecipe`），产物不固定，所以不进 PRODUCTS；
  传奇 × 传奇 由引擎的「同级合成」判定（rank 6 → rank 6，再抽传奇），不是额外配方。
- `TileMatcher` 支持 `{rank}` 与 `{variant}` 两种写法；Li+Na 是 `variant × variant` 配方，
  妙 是 `variant + rank`（彪 + 水³）配方，记会成 / 记赢赢×2 是 `variant × variant` 配方；
  `matches()` 对 variant 只比较词条 id，不看等级。
- 妙的爱心粒子是**纯表现**：`buff.id === 'miao'` 时，app.ts 在移动前记录棋盘上的妙，
  移动后按 `slides` / `merges` 算出妙的落格，再调用 `board.heartBurst(cells)`；
  创建当步不触发（增益从下一步生效）。粒子在妙所在格生成、跟随妙移动；
  如果这一步把妙合掉了，就落在合成后的格子。不新增存档字段，读档后按 `buffs` 里的 `miao` 恢复。

> **隐藏契约（重要）**：真通关配方（记 + 赢² → 记赢赢）是隐藏内容，游戏内不得提示——
> 记方块的词条池定义里**不写** `recipe`（不显示 +赢² 角标）；合成链页在该产物首次触发前
> **整行隐藏**；假通关弹层与「关于」简介都不写配方；棋盘提示只写「词条之间藏着特殊组合」。
> v2.5 的延伸配方（记赢赢 + 会成 → 记会成）同样属于隐藏链：合成链行要等 `ji-ying-ying`
> 首次收集后才显示（`SpecialProduct.revealAfter`），产物名在 `ji-hui-cheng` 触发前仍打码。
> 隋/圈隋 的 +军、钢的 +隋、彪的 +水³ 提示可以保留（非真通关内容），Li+Na / 隋+钢 / 彪+水³
> 配方行也公开（产物首次触发前打码）。改 UI/文案时别把隐藏配方加回去（测试里有专门断言）。
> v3.0 的传奇抽取（记赢赢 × 记赢赢）同样依赖真通关隐藏产物：合成链里的「传奇 · 相撞即合」整节
> 要等 `ji-ying-ying` 首次收集后才出现，未现世的传奇名字走问号 mini；「传奇」这个稀有度名可以在
> 图鉴分区里出现，但不得写「记赢赢 × 记赢赢」配方到假通关 / 关于 / 开场等任何公开文案里。

### 4.3 生成规则

- 每次有效移动后随机空格生成一枚：90% 军 / 10% 赢²（DEFAULT_SPAWN）。
- 开局 2 枚，分数 0，无增益，won/trueWon 均 false。

### 4.4 假通关 / 真通关

- 首次合出 OLD FIVE → justWon=true，won=true 持久化，弹「真通关了吗？」（礼花），不重复弹。
- 首次合出 记赢赢 → justTrueWon=true，trueWon=true 持久化，弹「真·通关！」（更大礼花），不重复弹。
  **游戏内不提示这个配方如何触发**（见 4.2 隐藏契约），弹层只在触发后解释。
- 弹层优先级：**传奇现世** > 真通关 > 假通关 > 首次收录解释 > 结束。
  v3.0 抽到传奇时先弹全屏 `kind=myth` 层（标题直接是词条名、大礼花），
  同一步的其它高优先级层（真/假通关、首次解释、结束）在它关闭后由 `onClose` 接续。
  结束层优先级最低但**必须补弹**：同一步同时无路可走且触发了解释卡 / 通关层时，先弹高优先级层，
  关闭后再由它的 `onClose` 补弹「无处可合」；结束层弹层被遮罩 / Esc 关掉后再操作会重新提示。
  判定以引擎的 `state.over`（每次有效移动、生成新方块后用 `canMove` 重算）为准，上面这条只是显示顺序。
- 本局失败音效（v2.4.1）：只在 `over` cue 播放独立音源；每个死局只播一次（`overAnnounced` 去重，
  重开 / 撤销后复位），遮罩关闭后再次提示结束层时不重复播。
- 撤销按快照恢复 won/trueWon/buffs（与原版语义一致）；图鉴收录永不回退。

### 4.6 存档与撤销

- localStorage key（前缀 jun2048 不变）：
  - `jun2048`：棋局（SavedGame **v3**）
  - `jun2048.best`：最高分
  - `jun2048.codex`：图鉴 `{ [entryId]: count }`（含特殊产物 id）
  - `jun2048.theme`：外观偏好 auto/light/dark
  - `jun2048.sound`：声音开关 on/off（v2.2.1 新增；缺省视为 on，旧档不受影响）
  - `jun2048.version`：上次进入游戏时的版本（v2.3.0 新增；只用于更新后弹一次版本号变化）
- v2.4 **没有新增 localStorage key**：妙的增益与爱心都复用 `jun2048` 里的 v3 `buffs`，
  图鉴进度条由已收录数量实时算出，不单独存档。
- v2.5 / v3.0 **也没有新增 key / 不改 SavedGame v3 字段**：新词条只进 `jun2048.codex`（按 id 收录），
  记会成 / 传奇的增益（没有传奇增益）走现有 v3 `buffs`；传奇方块用现有 `ranks`（值 6）+ `variants`
  字段即可，不需要升 v4。旧档读入后图鉴分母自动变成 48（旧记录全部保留）。
- 开场界面每次打开页面都出现一次；「继续游戏」由是否有棋局存档决定。
  全新玩家在启动时会先记下当前版本（`jun2048.version`），避免初始化写入的棋局把自己误认成老玩家。
- 等级签名 `jun|win|water|lec|liu`（liu 是 OLD FIVE 的存档身份，改名不改 id）。
- v3 兼容读 v1/v2；**词条 / 传奇 variant 必须存在于当前对应池子**（rank 5 = 词条池或特殊产物、
  rank 6 = 传奇池），否则整档判坏（换池子后旧档开新局）。rank 6 放普通 id、rank 5 放传奇 id 都判坏档。
- 每步移动后立即存档；pagehide 再存；存档失败不影响游戏。
- 撤销最多 20 步整局快照；撤销后最高分不回退、图鉴不回退。
- v2.3 改名兼容：旧档 buff 里的 label 是快照文案，`deserialize` 会按当前增益定义刷新 label
  （如「隋军·蓄水」→「水军·蓄水」），只改文案、不改倍率与步数；未知 id 的自定义增益保持原样。
- 无路可走 → over=true 弹结束层；读档死局启动时也弹，但 **开场界面开着时先不弹**，
  等玩家点「继续游戏」后再弹（app.ts 的 pendingGameOver）。
  结束层被高优先级弹层挡住时会延迟补弹；被遮罩 / Esc 关掉后再操作会重新弹出（不重复播失败音效）。

### 4.7 输入与交互

### 4.8 音频（合成音效 v2.2.2 · 失败音效 v2.4.1）

- **v2.3 回滚说明**：曾把原语音剪成三段不同音色（短喵 / 上扬 / 长喵呜），用户试听后
  完全不满意；现已**完整回滚到 v2.2.2 实现**（文件与提交内容一致）。以后动音效前，
  先做试听方案让用户选，别直接改默认声音。v2.4.1 没有改合成音源。
- 合成音源：用户微信语音「语音 010_W_20261102_092315.m4a」的**第二声猫叫**（1.15s–2.05s），
  经 ffmpeg 降噪（`afftdn`）、高通、`loudnorm` 归一化，转 64kbps 单声道 mp3，
  base64 内联在 `src/ui/merge-sfx.ts`（由 `scripts/audio.mjs` 生成，勿手改）。
- 失败音源（v2.4.1）：用户提供的「标准录音 1.mp3」（原始副本在 `release/audio-src/`，不进仓库）。
  处理流程：**先解码成 48k 单声道 wav**（源 mp3 首帧损坏，先修再处理）→ 裁 0.56s–2.80s
  （去掉开头约 0.56s 录音静音/底噪）→ 70Hz 高通 + 14kHz 低通 → `afftdn=nr=14:nf=-42`
  → `loudnorm=I=-14:TP=-1.0`（比合成音效的 -18 响约 4 dB）→ 首尾淡入淡出 →
  44.1k 单声道 64kbps mp3 → base64 内联在 `src/ui/over-sfx.ts`（约 18 KB mp3 / 24 KB base64）。
  重新生成：`node scripts/audio.mjs over <源音频> [起始秒] [结束秒]`（默认 0.56–2.80）。
- `src/ui/audio.ts` 的 `createAudio({w})` 返回 `AudioEngine`：`unlock / play / setEnabled /
  setVolume / startMusic / stopMusic / destroy`，app.ts 调用点不变；`unlock()` 时同时解码两段音源。
- 发声 cue：合成类 merge（原声）、special（×1.12）、win（×1.22）、truewin（×1.32）使用合成音源；
  本局失败 over 使用**独立的失败音源**（原速、播放增益 1.0，音源归一化到 -14 LUFS，比猫叫更突出）。
  move / invalid / undo / restart / collect / start 静默；一次移动里有多次合并也只播一次。
- **互斥（热更新）**：`playSfx` 用 `Voice` 跟踪正在响的声部——over 出现前先 `gain=0` + `stop()`
  停掉全部 merge 声部，再播失败音效；本步已经判负时 app 直接把 cue 改成静默的 move，不再发猫叫；
  新的合成音效开始时停掉失败音效尾音。不要改回「两段同时 start()」。
- 失败音效每个死局只播一次（app.ts 的 `overAnnounced` 去重；重开 / 撤销后复位），
  结束层被遮罩关掉后再次操作提示结束时不重复播放（4.4）。
- 解锁：app.ts 在「开始合成 / 继续游戏」时调用 `unlock()`；无 AudioContext（旧浏览器 / jsdom）
  时全部安全降级。解码用回调式 `decodeAudioData`，兼容 Safari 14.1。
- 声音开关：底栏 `#btn-sound`（🔊 / 🔇）调用 `setEnabled()`，偏好写 `jun2048.sound`（on/off，缺省 on），
  重开页面恢复；音量本身不持久化。这是第 5 个 localStorage key（4.6）。
- `startMusic()` 目前只记状态，不播背景音乐。
- 单文件契约：音频只能是 data URI / WebAudio 合成，不能外链；`verify-dist` 会检查
  合成 + 失败两段内联音效都存在。

### 4.9 版本更新弹窗（v2.3.0）

- 记录 key：`jun2048.version`（第 6 个 localStorage key）。启动时只读推导，**进入游戏时**才写入当前版本。

## 8. 踩过的坑（别踩回去）

1. **String.replace 的 $& 陷阱**：内联压缩 JS 必须用函数替换 `html.replace(marker, () => content)`。
2. **esbuild target**：用 safari14.1（safari14 报 destructuring 不支持）。
3. **jsdom 跨 realm**：state.cells / state.buffs 是页面领域数组，deepStrictEqual 会误判；
   用 Array.from(...) 或长度/逐项断言。
4. **jsdom 没有布局**：clientWidth 为 0，layout() 宽度 ≤0 直接返回；ResizeObserver 需 'ResizeObserver' in w 保护。
5. **localStorage 可能抛异常**：storage.ts 的 KV 必须 try/catch 退回内存。
6. **弹层过渡**：先 hidden=false → 强制 reflow（void offsetWidth）→ 加 is-open。
7. **弹层文案不要写 Markdown 星号**：textContent 会原样显示。
8. **词条方块必须有合法 variant**：v3 读档时 variant 不在池/特殊表 → 整档判坏（换池子的设计如此）。
9. **加词条不影响棋局存档**：签名只含等级 id；图鉴按 id 独立存、读档过滤。
   但**加词条会让图鉴总数、抽取权重、以及测试里的固定期望值变化**，改池子后要同步 tests 与文档。
10. **npm test 依赖 dist**：先 build 再 test，别拆。
11. **CSS 压缩会去掉属性选择器引号**：[data-theme="dark"] → [data-theme=dark]，
    静态自检的正则要兼容两种写法。
12. **增益展开别带定义字段**：BuffDef 有 moves，Buff 只有 movesLeft；
    构造 Buff 时逐字段赋值，不要 {...def, movesLeft}（会把 moves 带进存档）。
13. **深色 token 有两份**：@media 块与 [data-theme=dark] 块内容必须同步改（v2.1 的 --intro-veil 也是）。
14. **真通关是隐藏内容**：别在记方块的 `recipe`、合成链、假通关文案、关于简介里写
    「记 + 赢²」；测试里专门断言了这些位置不含泄露文案。
15. **开场界面会挡住输入**：所有棋盘输入都要过 `intro?.isOpen()` 守卫；
    jsdom 测试 boot() 默认自动跳过，新测试别忘。读档死局要等进入游戏再弹结束层。
16. **variant×variant 配方**：Li+Na 是两个 `{variant}` matcher；`matches()` 只比较 id，
    不要求 rank，但两枚实际都是 codexRank。加同类配方照这个写法即可。
17. **词条色相有两层来源**：显式 hue/hue2 优先；特殊产物不在抽取池里，所以 board/sheet 用
    `huesOf(entry, entries, id)`（传 entry 对象），不要只传 `config.codex.entries` 查特殊产物。
18. **音频接口的坑**：不要在 `createAudio` 构造时创建 AudioContext（会被自动播放策略拦），
    等 `unlock()`；也不要在 play 里写存档。单文件不能引外部音频，只能 data URI / WebAudio 合成。
19. **GitHub 仓库名只支持 ASCII**：试图把仓库名改成「疯狂水立方」会被归一成 `-`，
    API 返回 200 但名字已坏（真实 slug 是 `crazy-water-cube`，中文名只能写在简介/描述里）。
    v2.5 起 Gitee 路径也改成了 `crazy-water-cube`（不再是 `jun2048`），两个平台 owner 都是 `idealismo10`。
20. **音频必须内联**：`merge-sfx.ts` 里的 base64（约 10 KB）由 `scripts/audio.mjs` 生成，
    构建时随 JS 一起进单文件；不要改成外链 mp3/m4a。`verify-dist` 检查 data URI 与
    `decodeAudioData`。重新裁剪音频后要重跑 `npm run verify`，并确认单文件体积仍在可接受范围
    （v2.3 单文件约 109 KB）。
21. **无 AudioContext 必须静默**：jsdom 和旧浏览器没有 AudioContext；`createAudio` 不能因此抛错。
    解码用回调式 `decodeAudioData`（Safari 14.1 的 promise 式不保证），且只在 `unlock()` 后创建。
22. **加词条会动测试固定值**：随机池 14→17 时，权重总和 31→37、固定 rng 抽中项从「红梅」变「金山」；

    用户看完直接说「显得低级、完全不满意」。定稿改成：低饱和水彩玻璃色板（稀有 50% / 传说 46%）、

    在关闭后补弹结束层；死局弹层被遮罩 / Esc 关掉后再操作会重新提示；失败音效用 `overAnnounced`
    去重（重开 / 撤销复位）。tests/ui.test.ts 有两条回归，别把结束层放回 else-if 链末尾。
34. **音频源文件可能首帧损坏**：用户给的「标准录音 1.mp3」解码时报 `Header missing`

36. **失败音效与猫叫互斥**：只在 app 里把本步 cue 改成静默还不够——上一步的猫叫可能还在响。

    产物名在 `ji-hui-cheng` 触发前仍走问号 mini。不要在 `会成` 上加 `+记赢赢` 角标。
38. **传奇是 rank 6，不是 rank 5**：v3.0 把传奇放在 `codexRank + 1`（`mythRank`），
    用 `isMythRank` / `isVariantRank` 判断，不要把传奇塞进词条池或当成 rank 5：
    - rank 5 放传奇 id、rank 6 放普通 id 都会在 `deserialize` 判坏档；
    - `justWon` 必须排除 variant 等级，否则合出传奇会被误判成假通关；
    - 传奇只能和传奇合（rank 6 × rank 6 → 再抽传奇），与 rank 5 不相合；
    - 棋盘/图鉴的 mini 渲染用 `isVariantRank`，CSS 给 `data-rarity="myth"` 单独的材质。
39. **传奇抽取走 MYTH_RECIPES，不是 PRODUCTS**：产物是随机的，`pairResult` 返回 `kind:'myth'`，
    `move` 从 `config.codex.myths` 用 `drawCodexEntry` 抽（权重均匀 1），落成 rank 6；
    没有增益，得分 512。`matchMythRecipe` 要放在 `matchRecipe` 之前，否则会被同级判定吃掉。

    全收录卡片数 48、1/48 进度 2%、`mythRank=6`；测试里搜 36 / 48 / `mythRank` 一起改。

## 9. 可自由重写 vs 建议保留

**建议保留（契约层）**
- engine.ts 纯函数接口与第 4、5 节规则语义；recipes/buffs 的配置形态。
- 六个 localStorage key（v2.2.1 起含 `jun2048.sound`，v2.3.0 起含 `jun2048.version`）、
  SavedGame v3 字段、tiersSignature 规则。
- 第 5.5 节 DOM id/class 契约；tests/ 是规则的事实文档。
- 失败判定：`state.over` 由引擎负责；UI 的结束层补弹 / 重提示 / 失败音效去重逻辑（4.4、踩坑 33）。

- 隐藏契约（真通关配方不提示；记会成延伸配方在记赢赢解锁前也不提示）。

**可以放心重写（表现层）**
- main.css 全部视觉（保持 token 双块同步与契约 class）。
- ui/ 各模块的内部实现（保持 AppApi、DOM 契约、交互行为、弹层优先级、开场界面行为）。
- index.html 结构（保持 id 与内联占位）。
- 开场界面与「关于」的具体文案/排版（别泄露隐藏配方）。
- `ui/audio.ts` 的内部实现（保持 AudioEngine 方法与 cue 名称，app 的调用点不用改）；
  音源重新生成只改 `scripts/audio.mjs` 的预设 + 重跑脚本。
- 构建设计（仍产出单文件、无外部资源、file:// 可跑）。

**验收标准**

建议流程：

1. **先读本文件**，尤其是第 4、5 节（机制契约、数据结构）和第 9 节（哪些能重写）；
   不要凭猜测改机制，机制以 `tests/` 为准。
2. **动手前先确认改动边界**：改的是机制、视觉、交互还是发布链路？哪些契约必须原样保留？
   用户只说「随便改」时，先给一个最小方案再动手。
3. 改动写在 `src/`（`lore.ts` / `meta.ts` 是「用户只改这一个文件」的约定位置）；
   新行为先补/改 `tests/`，再跑 `npm run verify`。
4. `npm run pack` 刷新 `/sdcard/Download/DSH-Go/` 的发布件（单文件 / 源码包 / 说明文档）。
5. 要发新版：改 `meta.ts` 的 `GAME_VERSION` + `package.json` 的 version → 提交并推 `main` 到
   两个仓库 → 打 `vX.Y.Z` 标签推两个仓库 → 按 7.1 建发行版并核对哈希 → 按 7.2 刷新 Pages。
   **习惯：刷新 Pages / 大规模发布前先跟用户说一声。**
6. **硬红线**：真通关配方（记 + 赢²）不得在游戏内提示或写进任何玩家可见文案；
   记会成延伸配方 / 记赢赢×2→传奇 在记赢赢解锁前同样不得显示；单文件不能引外部资源；
   动画只用 CSS transform / transition；存档六个 key 与 v3 字段不要乱改（传奇复用 ranks=6 + variants，
   不要为了它升 SavedGame 版本）。

交付时用两三句话说明：改了什么、没动什么、已知取舍；**没做真机目视验证就不要声称做过**。
